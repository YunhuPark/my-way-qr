## 번호

## 제안자의 의도 (답변 요지)
| 주제 | 제안자 답변 |
|---|---|
| 우선 어려움 유형 | "사용자 정보에 따라 다르다" (특정 유형을 고정하지 않음) |
| 우선 적용 업종 | **카페·식당류** (일상 편의가 목적) |
| QR 방향 | 양방향이 이상적. 하나만 한다면 **키오스크에 QR이 뜨고 사용자 휴대폰으로 스캔**하는 쪽이 더 편할 것 |
| 초기 시제품 환경 | 앱에 SDK를 넣거나 화면을 수정할 수 있는 환경을 전제해도 됨 |
| **AI 화면 변환** | 미리 저장한 화면만 고르는 방식이 아니라, **AI가 실시간으로 화면을 변환**할 수 있어야 함 (임의의 키오스크에 적용하려면 조건별 화면을 AI가 만들어야 하므로) |
| 터치 보정 | 버튼·터치 영역 **확대** 정도. 개인 터치 패턴 분석까지는 불필요 |
| 우선순위 | 한 화면에 안 담기면 **글씨 > 버튼 > 자세한 설명**. 스크롤 유도 활용. 극단적 경우는 직원 도움 |
| 시연 범위 | 실제 접수·결제 연동 불필요. **모의 서버로 충분**. 화면 변환의 **성공률**이 더 중요 |

## 현재 프로토타입과의 대조
| 항목 | 현재 | 차이 |
|---|---|---|
| 업종 | 카페·민원·병원 | 카페는 있음. 식당은 없음 |
| QR 방향 | 사용자 프로필 QR을 휴대폰으로 스캔 → 휴대폰에서 키오스크 화면이 열림 | 제안자가 선호한 "키오스크 화면의 QR을 사용자가 스캔"과 다름 |
| AI 역할 | 말→프로필 설정, 문구를 쉬운 말로 재작성 | **화면 구조(버튼 배치·설명 단계) 변환은 AI가 아님.** 시나리오는 미리 정의, 레이아웃은 CSS 규칙 |
| 글씨·버튼 우선 | 글자 배율에 맞춰 버튼도 함께 커짐 | 우선순위 규칙(글씨>버튼>설명)과 스크롤 유도는 명시적으로 구현하지 않음 |
| 변환 성공률 | 측정 없음 | 사용자 테스트와 별개로 "변환 성공률"을 재는 방법이 필요 |

## 제안서(5번) 핵심 — 제안자가 쓴 목표와 설계 요소
출처: `forms/proposals/p5.pdf` (2026 AI 라이프 아이디어 챌린지 수상후보작 제안서). 아래는 제안자의 원안이며 공고문의 필수 요건은 아니다.

| 제안서의 요소 | 현재 구현 |
|---|---|
| MVP: 큰 글씨·쉬운 말·음성·터치보정 4개 + QR 프로필 | 큰 글씨(배율)·쉬운 말(AI)·음성·고대비·단계·시간 연장, QR 프로필 구현. 터치보정은 "버튼 영역 확대"(글자 배율과 함께 커짐) |
| **AI 화면 재배치** (복잡한 문장을 단계화, 중요 기능 우선) | **구현:** AI 화면 변환(`/transform.html`) — 단계 나누기, 쉬운 말 |
| **기기 적합성 검사** (지원 불가 기능은 직원 호출) | **구현:** 화면만으로 끝낼 수 없는 선택지를 `staff`로 표시, 🙋 직원 도움 안내 |
| **안전 확인** (결제·제출 전 선택 내용 재확인) | **구현:** 변환 화면에서 선택 내용 확인 단계 |
| **변환 오류 방지** (원거래 내용·가격을 바꾸지 않고 결제 전 원문 확인) | **구현:** 확인 단계에 원문 병기 + 가격·숫자 자동 검사(통과 못 하면 사용 불가) |
| 최소 공유 (장애명 없이 기능 코드만) | 구현: 프로필에는 선호 설정만 |
| 사용 종료 시 프로필 삭제 | 부분: 프로필은 서버에 저장되지 않고 주소(URL)에만 있음. 세션 종료 시 삭제하는 기능은 없음 |
| 운영자 리포트 (개인정보 없는 기능 집계) | 미구현 |
| 성능 한계 공개 | 보고서에 "모의 환경, 소규모 탐색 테스트"로 명시할 것 |
| **솔루션 챌린지 목표**: 2개 이용과제 MVP에서 **독립 완료율 30% 향상, 도움요청 절반 감소** 검증 | 사용자 테스트 지표와 동일: 독립 완료율(=도움 없이 성공 비율), 도움 요청 횟수. 병원 접수·무인결제 과제 → 우리 병원·카페 과업 |
| 실증 설계: 도입 전 기준값을 먼저 측정, 동일 과업 반복, 인터뷰·관찰 병행 | 우리 설계: 기본 화면(기준)과 내 방식 화면을 같은 사람이 비교, 인터뷰 포함 |
